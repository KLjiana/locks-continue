# Locks Continue Lockpicking Rewards Implementation Guide

[简体中文](reward-system-guide.md) | English · [Documentation](README.md)

## 1. Purpose

This document defines lockpicking performance metrics, failure thresholds, reward tiers, loot generation, data-pack formats, server state, compatibility behavior, and acceptance criteria for Locks Continue.

This is an implementation specification. Code should follow the boundary semantics defined here; fields and classes not yet present in the project are to be added incrementally.

Initial scope:

- Use the mod's built-in Java logic for server validation and reward distribution.
- Use native data packs to define failure thresholds, reward tiers, and additional loot tables.
- Support vanilla containers, double chests, barrels, shulker boxes, and integrated Lootr containers.
- Do not implement a KubeJS API yet, but keep the data structures open to future extension.

## 2. Established Rules

1. Pin, rotary, and memory locks grade performance by mistakes during the current valid attempt.
2. Pipe locks grade completion time, not rotation count or incorrect orientations.
3. A pipe puzzle succeeds when matching pipe connections form routes from the start to all targets. Ordinary branches, empty cells, and unrelated dead ends do not affect success or failure by default.
4. Data packs can define how many mistakes or ticks qualify for each reward tier.
5. Data packs can define how many mistakes or ticks cause an attempt to fail.
6. `failure_at = -1` means that grading metric does not cause failure.
7. `-1` disables only metric-based failure. Tool breakage, lock removal, moving out of range, changing dimensions or tools, and invalid sessions can still end a session.
8. Rewards can add complete rolls of the container's original source loot table and append separate reward loot tables.
9. The server calculates all metrics, failures, and reward tiers. Clients cannot submit elapsed time, total mistakes, reward tiers, or claims that they should receive a reward.
10. A generated lock's reward configuration is fixed. Reopening the GUI or running `/reload` cannot refresh its saved reward rules.
11. Each lock may settle a successful reward only once.

## 3. Key Terms

| Term | Meaning |
| --- | --- |
| `source_loot_table` | The container's original loot table, such as `minecraft:chests/ancient_city` |
| `reward_profile` | Resource ID of a reward configuration in a data pack |
| `metric` | Grading method; initially `mistakes_used` or `time_ticks` |
| `metric_value` | Mistakes or elapsed time used by the current valid attempt |
| `failure_at` | Reaching this value fails the attempt; `-1` disables this reward rule's own failure threshold |
| `tier` | A reward tier |
| `max` | The tier's inclusive upper bound for the metric |
| `source_rolls` | Total complete rolls of the original source loot table |
| `source_luck_bonus` | Minecraft luck added only to additional source-table rolls |
| `bonus_loot_table` | Optional separate reward loot table |
| `bonus_rolls` | Number of rolls of the separate reward table |
| `reward_claimed` | Whether the successful reward has been settled; prevents duplicate distribution |

`source_rolls` does not modify the `rolls` expression of a pool inside a vanilla loot table. It tells the server how many times to generate the entire source table.

For example:

```text
source_rolls = 1  Generate the original table normally once
source_rolls = 2  Keep the normal first roll and add one extra roll
source_rolls = 3  Generate the original table three times in total
```

Additional source-table rolls pass `source_luck_bonus` as extra luck. This does not modify loot already generated by the original roll. Entries with positive `quality` receive increased weights; fixed probability conditions such as `random_chance` keep their original probabilities. The default is `2.0` when `source_rolls > 1`, otherwise `0`. Explicit `0` disables the bonus; the valid range is `0–20`. Saved tiers without this field receive the same default when loaded.

## 4. Metrics for the Four Minigames

| Lock type | `metric` | When the metric increases | Preferred result |
| --- | --- | --- | --- |
| `lockscontinue:pin` | `mistakes_used` | The server returns a valid `MISTAKE` | Lower is better |
| `lockscontinue:rotary` | `mistakes_used` | The server recognizes pressure or a wrong attempt as a valid failure | Lower is better |
| `lockscontinue:memory` | `mistakes_used` | The server confirms a mismatched pair | Lower is better |
| `lockscontinue:pipe` | `time_ticks` | Every server tick after the first valid rotation | Lower is better |

The following must not increase `mistakes_used`:

- Duplicate packets.
- Expired action sequences.
- Clicking a nonrotatable cell.
- Client/server state mismatches.
- The player no longer being near the target container.
- Completed or invalid sessions.
- Any action returning `REJECTED`.

Pipe timing starts with the first server-accepted `PIPE_ROTATE`, not when the GUI opens. Reading the interface or resizing the window therefore does not consume reward time.

## 5. Failure Semantics

### 5.1 Mistake-Based Minigames

Whenever the server puzzle returns `MISTAKE`:

1. Increment `mistakes_used` by one.
2. Apply the tool durability cost for that mistake.
3. If `failure_at >= 0` and `mistakes_used >= failure_at`, fail the attempt and close the GUI.
4. Otherwise, continue the game.

Example:

```json
{
  "metric": "mistakes_used",
  "failure_at": 4
}
```

A successful attempt may have `0`, `1`, `2`, or `3` mistakes. The fourth valid mistake fails the attempt.

### 5.2 Time-Based Minigames

On the pipe lock's first valid rotation, record:

```text
metric_started = true
started_at = serverLevel.getGameTime()
```

The current time metric is:

```text
elapsed_ticks = serverLevel.getGameTime() - started_at
```

Pipe locks obey both the difficulty's `pipe.time_limit_ticks` and a time-based reward rule's `failure_at`. The shorter enabled value is the effective time limit. The difficulty limit defaults to `1200` ticks (60 seconds), with a valid finite range of `20–7200`. Each limit can independently be disabled with `-1`; time is unlimited only when both are disabled. If rewards use `mistakes_used`, their `failure_at` still represents mistakes, while the difficulty's pipe timer applies independently.

When `elapsed_ticks >= effective time limit`, the attempt fails. A timeout applies the configured failure durability cost once, never repeatedly on later server ticks.

Active sessions must check deadlines on server ticks, not only on the next player click. Otherwise, stopping input would prevent the timer from ever failing the attempt.

### 5.3 Disabled Failure Thresholds

```json
{
  "failure_at": -1
}
```

This means:

- This reward rule no longer fails an attempt through its own metric. For pipe locks, `pipe.time_limit_ticks` still applies independently; disable that limit with `-1` as well for unlimited time.
- The final metric still determines the reward tier.
- A tool can still break from durability costs on valid mistakes.
- Invalid sessions are still rejected by the server.

## 6. Reward Tier Matching

Sort tiers by increasing `max` and select the first tier satisfying:

```text
metric_value <= tier.max
```

The `max` boundary is inclusive.

Example:

```json
{
  "tiers": [
    { "max": 0, "source_rolls": 3 },
    { "max": 1, "source_rolls": 2 },
    { "max": 3, "source_rolls": 1 }
  ]
}
```

Result:

| Metric value | Selected tier |
| ---: | --- |
| 0 | `max = 0` |
| 1 | `max = 1` |
| 2–3 | `max = 3` |

If an attempt succeeds without matching any tier and has not reached a failure threshold, use the safe fallback:

```text
source_rolls = 1
bonus_rolls = 0
```

Do not automatically reuse the last high-reward tier. With `failure_at = -1`, that could grant extra rewards even after arbitrarily many mistakes.

## 8. Complete Reward Configuration Format

A reward profile can select different rules by lock type and difficulty. Match rules in file order and use the first matching rule.

```json
{
  "schema": 1,
  "rules": [
    {
      "match": {
        "lock_types": [
          "lockscontinue:pin",
          "lockscontinue:rotary",
          "lockscontinue:memory"
        ]
      },
      "metric": "mistakes_used",
      "failure_at": 4,
      "tiers": [
        {
          "max": 0,
          "source_rolls": 3,
          "source_luck_bonus": 2.0,
          "bonus_loot_table": "lockscontinue:bonus/perfect",
          "bonus_rolls": 2
        },
        {
          "max": 1,
          "source_rolls": 2,
          "source_luck_bonus": 2.0,
          "bonus_loot_table": "lockscontinue:bonus/good",
          "bonus_rolls": 1
        },
        {
          "max": 3,
          "source_rolls": 1,
          "bonus_rolls": 0
        }
      ]
    },
    {
      "match": {
        "lock_types": ["lockscontinue:pipe"],
        "difficulties": [
          "lockscontinue:simple",
          "lockscontinue:normal"
        ]
      },
      "metric": "time_ticks",
      "failure_at": 600,
      "tiers": [
        {
          "max": 120,
          "source_rolls": 3,
          "bonus_loot_table": "lockscontinue:bonus/fast",
          "bonus_rolls": 2
        },
        {
          "max": 240,
          "source_rolls": 2,
          "bonus_loot_table": "lockscontinue:bonus/good",
          "bonus_rolls": 1
        },
        {
          "max": 599,
          "source_rolls": 1,
          "bonus_rolls": 0
        }
      ]
    },
    {
      "match": {
        "lock_types": ["lockscontinue:pipe"],
        "difficulties": [
          "lockscontinue:hard",
          "lockscontinue:expert",
          "lockscontinue:master"
        ]
      },
      "metric": "time_ticks",
      "failure_at": 1200,
      "tiers": [
        { "max": 300, "source_rolls": 3 },
        { "max": 600, "source_rolls": 2 },
        { "max": 1199, "source_rolls": 1 }
      ]
    }
  ]
}
```

These time values illustrate the format, not final balancing. Actual gameplay testing must determine the final defaults.

### 8.1 `match`

Supported fields:

```json
{
  "lock_types": ["lockscontinue:pipe"],
  "difficulties": ["lockscontinue:master"]
}
```

- Omitting `lock_types` matches every lock type.
- Omitting `difficulties` matches every difficulty.
- Arrays contain resource IDs, not display names.
- Since the first match wins, place specific rules before general ones.

### 8.2 `metric`

Initially accepted values:

```text
mistakes_used
time_ticks
```

An invalid value rejects the reward profile file, but must not crash the server.

### 8.3 `failure_at`

- `-1`: Disable this reward rule's own failure threshold, not the difficulty's pipe timer.
- Mistake-based rules accept `1–100000`.
- Time-based rules accept `1–72000`, up to one hour of game ticks.
- `0` has no valid meaning and is a configuration error.

### 8.4 `source_rolls`

- Defaults to `1`.
- Recommended allowed range: `1–5`.
- Counts total source-table rolls, not extra rolls.
- Without a `source_loot_table`, treat this as `1`. It cannot copy items already inside the container.

### 8.5 `source_luck_bonus`

- Defaults to `2.0` when `source_rolls > 1`, otherwise `0`.
- Valid range: `0–20`. Explicit `0` disables the bonus on extra rolls.
- Applies only to the `source_rolls - 1` additional source-table rolls, not the normal first roll or a separate `bonus_loot_table`.
- Uses Minecraft's Luck parameter to increase weights of entries with positive `quality`. Entries using fixed random probability conditions are unaffected.

### 8.6 `bonus_loot_table`

- Optional resource ID.
- Required only when `bonus_rolls > 0`.
- If the table is missing, skip the extra reward and log an error including its resource path.
- A missing reward table must not prevent the original container from unlocking.

### 8.7 `bonus_rolls`

- Defaults to `0`.
- Recommended allowed range: `0–5`.
- A positive value requires `bonus_loot_table`.

## 9. Referencing Reward Profiles from Loot Rules

Add an optional field to `loot_rules`:

```json
{
  "priority": 100,
  "match": {
    "loot_tables": ["minecraft:chests/ancient_city"]
  },
  "lock_chance": 0.9,
  "lock_types": {
    "lockscontinue:rotary": 3,
    "lockscontinue:memory": 1
  },
  "difficulties": {
    "lockscontinue:hard": 3,
    "lockscontinue:master": 1
  },
  "reward_profile": "lockscontinue:ancient_city"
}
```

Resolution order:

1. Use the `reward_profile` explicitly selected by the matching `loot_rules` entry.
2. If omitted, use `lockscontinue:default`.
3. If the requested profile is missing, log an error and use safe fallback rules.

Safe fallback rules:

```text
metric          By lock type: time_ticks for pipes, mistakes_used for other locks
failure_at      Use the existing difficulty failure limit; -1 for pipes
source_rolls    1
bonus_rolls     0
```

The fallback pipe reward's `failure_at: -1` does not disable the difficulty's `pipe.time_limit_ticks`.

## 10. Persistent Data Model

### 10.1 Lock Instance

Upgrade `LockInstance` to schema 2 and save the resolved reward snapshot:

```java
record LockInstance(
    int schemaVersion,
    ResourceLocation lockType,
    ResourceLocation difficulty,
    long seed,
    ResourceLocation sourceLootTable,
    List<ResourceLocation> affixes,
    ResourceLocation rewardProfile,
    ResolvedRewardSnapshot rewardSnapshot
) {}
```

NBT example:

```snbt
lockscontinue_lock: {
  schema: 2,
  type: "lockscontinue:pipe",
  difficulty: "lockscontinue:hard",
  seed: 123456L,
  source_loot_table: "minecraft:chests/ancient_city",
  affixes: [],
  reward_profile: "lockscontinue:ancient_city",
  reward: {
    schema: 1,
    metric: "time_ticks",
    failure_at: 1200,
    tiers: [
      {max: 300, source_rolls: 3, bonus_rolls: 0},
      {max: 600, source_rolls: 2, bonus_rolls: 0},
      {max: 1199, source_rolls: 1, bonus_rolls: 0}
    ]
  }
}
```

Saving the complete resolved reward rules instead of only `reward_profile` ensures that reward-rule reloads affect newly generated locks only.

### 10.2 Reward Attempt State

Persist the attempt's performance so players cannot clear mistakes by closing and reopening the GUI, or reset pipe timing by reopening the lock.

Suggested state:

```java
record RewardAttemptState(
    UUID playerId,
    boolean metricStarted,
    long startedAt,
    int mistakesUsed,
    boolean failed
) {}
```

Save this state with the lock instance or in `SavedData` indexed by dimension, container position, and player UUID.

Rules:

- The same player reopening the same lock continues the existing attempt.
- Once pipe timing starts, closing the GUI neither pauses nor resets it.
- Closing the client screen does not clear mistakes.
- Reaching a failure threshold ends the attempt; the next attempt starts a new performance record.
- Other players may have separate attempt states, but the first successful player unlocks the container and invalidates other sessions.
- Both halves of a double chest share the same attempt state.

If persistent attempts are deferred in an initial implementation, closing the GUI must explicitly count as failure. Silently resetting metrics would allow unlimited retries for perfect rewards.

## 11. Java Type Design

Suggested types:

```java
enum RewardMetric {
    MISTAKES_USED,
    TIME_TICKS
}

record RewardTier(
    int max,
    int sourceRolls,
    ResourceLocation bonusLootTable,
    int bonusRolls,
    double sourceLuckBonus
) {}

record RewardRule(
    Set<ResourceLocation> lockTypes,
    Set<ResourceLocation> difficulties,
    RewardMetric metric,
    int failureAt,
    List<RewardTier> tiers
) {}

record RewardProfileDefinition(
    ResourceLocation id,
    List<RewardRule> rules
) {}

record ResolvedRewardSnapshot(
    ResourceLocation profileId,
    RewardMetric metric,
    int failureAt,
    List<RewardTier> tiers
) {}
```

Suggested responsibilities:

| Class | Responsibility |
| --- | --- |
| `LockDefinitionManager` | Load `rewards`, validate references, and resolve rules when creating locks |
| `RewardProfileDefinition` | Represent reloadable data-pack configuration |
| `ResolvedRewardSnapshot` | Store immutable resolved rules in locks and sessions |
| `RewardAttemptState` | Store a player's time or mistake performance for the current lock |
| `LockRewardResolver` | Select rules and tiers from lock type, difficulty, and configuration |
| `LockRewardDistributor` | Generate additional source-table rolls and reward tables without duplicate distribution |
| `LootrRewardBridge` | Add rewards to the player's individual Lootr inventory when Lootr is installed |

## 12. Session Fields

Add at least the following to `LockSessionManager.Session`:

```java
private final ResolvedRewardSnapshot reward;
private RewardAttemptState rewardAttempt;
private boolean rewardClaimed;
```

Do not calculate time using client GUI ticks. Pipe timing must use the server's `ServerLevel#getGameTime()`.

Store `mistakesUsed` explicitly rather than relying only on `initialMistakes - mistakesLeft`, because `failure_at = -1` may leave no finite `mistakesLeft` value.

## 13. Complete Server Flow

### 13.1 Generating a Lock

```text
Container receives a source loot table
        ↓
Match LootLockRule
        ↓
Select lock type, difficulty, and affixes
        ↓
Select reward_profile
        ↓
Resolve RewardRule from lock type and difficulty
        ↓
Create ResolvedRewardSnapshot
        ↓
Persist it with LockInstance
```

A double chest performs random selection and reward-rule resolution only once. Both halves save the same lock instance.

### 13.2 Starting a Session

1. Validate the player, tool, distance, dimension, chunk, and lock instance.
2. Read the lock's fixed `ResolvedRewardSnapshot`.
3. Read or create the player's `RewardAttemptState`.
4. Construct the server-side puzzle.
5. Send only the metric type, current value, and failure threshold needed for display.

### 13.3 Handling Actions

```text
Receive action packet
   ↓
Validate session and action sequence
   ↓
Has the pipe game reached its effective time limit? ── Yes → TIME_LIMIT failure
   ↓ No
Server puzzle handles the action
   ├─ REJECTED → No metric change or durability cost
   ├─ UPDATED/PROGRESS → Save puzzle state
   ├─ MISTAKE → mistakes_used + 1, then check the failure threshold
   └─ SOLVED → Settle rewards
```

After confirming the first valid `PIPE_ROTATE`, record that operation's server tick as the start time. Fail at the boundary `elapsed_ticks >= effective time limit`. Reward timing and the game countdown share this persisted start time.

### 13.4 Successful Settlement

On success, perform these steps in order:

1. Revalidate the lock, player, tool, and container group.
2. Confirm `reward_claimed == false`.
3. Calculate the final `metric_value`.
4. Select a reward tier, or use the safe fallback if none matches.
5. Mark reward settlement as in progress to prevent reentry.
6. Ensure the container's normal base loot generates only once.
7. Generate `source_rolls - 1` additional source-table rolls.
8. Generate `bonus_rolls` rolls of `bonus_loot_table`.
9. Mark `reward_claimed = true`.
10. Clear the container lock.
11. Send the success result, play the sound, and open the container normally.

Reward distribution and unlocking must form a server operation that cannot be repeated. Duplicate success packets, reopening menus, and client retries must not generate more rewards.

### 13.5 Failed Attempts

On failure:

1. Generate no rewards.
2. Keep the container locked.
3. Play the appropriate failure feedback.
4. Do not charge durability twice for the final mistake in a non-pipe game.
5. A pipe timeout charges the configured failure durability cost once.
6. Clear the session and mark the persistent attempt as failed.
7. Create a fresh performance record when the player attempts the lock again.

## 14. Loot Generation Requirements

### 14.1 Original Source Loot Table

Recommended procedure:

1. Let the container unpack its normal vanilla base loot once.
2. Generate additional rolls using `source_loot_table` and server-built `LootParams`.
3. Use a different deterministic seed derived from the lock seed for each roll.
4. Collect generated items in a temporary list, then merge them safely into the target container.

Illustrative seed derivation:

```text
rollSeed = mix(lock.seed, rewardTierIndex, rollIndex, lootTableId)
```

Do not reuse the same seed for every extra roll; that could produce identical rewards.

### 14.2 Separate Reward Table

`bonus_loot_table` uses the same unlocking player and container context, but an independently derived seed. Reward generation must not trigger lock generation again.

### 14.3 Insufficient Container Space

Initial policy:

- Never overwrite existing items.
- Merge compatible stacks first.
- Fill empty slots next.
- Drop remaining items at the container center with a normal pickup delay.
- Never silently delete high-tier rewards because a container is full.

### 14.4 Manually Locked Containers

Manually locked containers usually have no `source_loot_table`:

- `source_rolls` does not copy existing items.
- Treat `source_rolls` as `1`.
- A configured `bonus_loot_table` can still provide additional rewards.
- To prevent rewards from manual locks, toolbox installation should select a default profile without rewards.

## 15. Container Compatibility

### 15.1 Ordinary Single Containers

Chests, barrels, and shulker boxes unpack base loot and append rewards before unlocking and opening their menus.

### 15.2 Double Chests

- Use a normalized container-group position as the reward key.
- Settle rewards once across both halves.
- `source_rolls` and `bonus_rolls` apply to the combined container, not once per half.
- Synchronize the claim marker to both halves.

### 15.3 Lootr

Lootr typically generates loot per player. Do not write additional rewards directly into shared block-entity slots.

Requirements:

- No class-loading errors when Lootr is absent.
- Use an optional compatibility layer to add rewards to the individual Lootr inventory of the player who completes the lock.
- Identify the source for `source_rolls` through `LootTable` or `specialLootChest_table`.
- Save reward claim markers per player to prevent repeat claims.
- Other players opening the unlocked Lootr container later receive their ordinary Lootr loot, unless the data pack explicitly provides independent lockpicking for every player.

The initial default is: the player who completes the lock receives the performance reward.

## 16. Data-Pack Loading and Validation

When loading `rewards/*.json`, check at least:

- `schema` is supported.
- `rules` is a nonempty array.
- `metric` is recognized.
- `failure_at` is `-1` or a valid positive value.
- Tier `max` values are strictly increasing.
- `max` is nonnegative.
- With a finite failure threshold, every tier's `max` is below `failure_at`.
- `source_rolls` is within `1–5`.
- `bonus_rolls` is within `0–5`.
- A `bonus_loot_table` is provided when `bonus_rolls > 0`.
- Lock-type, difficulty, reward-profile, and loot-table resource IDs are valid.
- Every `reward_profile` referenced by `loot_rules` exists.

Error handling:

- One invalid file must not prevent server startup or `/reload`.
- Logs must identify the full resource path and the specific field.
- Invalid configurations use safe defaults, never free multiple source-table rolls.
- Data-pack priority determines which definition wins for the same resource ID.

## 17. Network Protocol and Client Display

Add or update these protocol fields:

```text
rewardMetric
metricValue
failureAt
metricStarted
pipeTimeLeftTicks
```

Both `OpenLockPacket` and `LockResultPacket` carry the server-calculated `pipeTimeLeftTicks`: `-1` means unlimited, `0` means time has run out, and positive values are remaining ticks. The client displays this countdown rather than inferring the pipe deadline solely from reward `failure_at`.

The client needs only display data for the status bar, not the identity of the loot table the server will generate.

Suggested status display:

```text
Pin lock: Mistakes 1 / 4
Pipe lock: Time 8.6s / 30.0s
Unlimited mode: Mistakes 7 / ∞
```

The client may use public tiers to display labels such as Perfect, Good, or Normal, but the server determines the final tier.

Clients must never submit:

- Final elapsed time.
- Total mistakes.
- Reward tier.
- Source-table roll count.
- Reward loot-table IDs.
- A declaration that rewards have already been claimed.

Bump the network protocol version whenever packet fields change to prevent incompatible clients from connecting.

## 18. Migrating Old Data

### 18.1 Schema 1 Lock Instances

Old locks have no reward fields. On first read:

1. Use their existing `lockType`, `difficulty`, and `sourceLootTable`.
2. Resolve a reward profile once from the current `loot_rules`.
3. Create a `ResolvedRewardSnapshot`.
4. Upgrade to schema 2 and save.

After migration, later `/reload` calls do not change that lock's reward.

### 18.2 Old Data Packs

Old `loot_rules` without `reward_profile` use `lockscontinue:default`. Existing lock probabilities, type selection, difficulty selection, and affix selection must remain intact.

The old difficulty fields `failure.mistakes` and `memory.mismatch_limit` provide fallbacks when no reward configuration is available. With reward rules present, mistake-based games use reward `failure_at` as their failure threshold. Pipe `pipe.time_limit_ticks` applies independently and combines with a positive time-based reward `failure_at` by taking the shorter value. Older packs that omit the difficulty time limit use `1200` ticks.

## 19. Security and Exploit Prevention

- Distribute rewards only after the server confirms `SOLVED`.
- Before unlocking, recheck that the container still has the same lock instance.
- Set `reward_claimed` atomically or with an equivalent idempotent operation.
- Duplicate packets cannot distribute rewards again.
- Closing the GUI cannot reset performance metrics.
- Disconnecting and logging back in cannot refresh those metrics.
- Changing tools or dimensions, or moving out of range, invalidates the session without silently clearing existing mistakes or the running timer.
- Data packs may specify only bounded `source_rolls` and `bonus_rolls`.
- Missing tables, full containers, or compatibility errors cannot cause repeated settlement.
- Additional generated loot must not trigger this mod's lock-generation events again.

## 21. Test Cases

### 21.1 Configuration Parsing

- Valid mistake-based configurations load.
- Valid time-based configurations load.
- `failure_at = -1` loads.
- `failure_at = 0` is rejected.
- Duplicate or unordered `max` values are rejected.
- Out-of-range `source_rolls` and `bonus_rolls` are rejected.
- Missing reward tables do not crash the server.
- Higher-priority data-pack definitions override the same ID.

### 21.2 Tier Selection

- A metric equal to `max` matches that tier.
- A metric between two tier bounds selects the later tier.
- With no matching tier, use the safe reward fallback.
- Reaching a finite `failure_at` prevents rewards.
- With failure disabled, a large metric does not automatically select the last high-reward tier.

### 21.3 Mistake-Based Games

- A valid pin timing mistake increments the count once.
- A valid rotary failure increments it once.
- A memory mismatch increments it once.
- `REJECTED` does not add a mistake.
- The final mistake charges durability once.
- Closing and reopening the GUI does not clear mistakes.

### 21.4 Pipe Games

- Opening the GUI does not start the timer.
- The first valid rotation starts it.
- Clicking the start, a target, or an empty cell does not start it accidentally.
- Ordinary branches and unrelated dead ends do not cause failure.
- Connecting the start to all targets succeeds.
- Reaching the time limit fails the attempt once.
- Closing and reopening the GUI keeps the timer running.
- A positive difficulty limit still causes failure when reward `failure_at = -1`.
- If both reward and difficulty time limits are positive, the shorter one applies.
- Reward `failure_at = -1` and difficulty `time_limit_ticks = -1` disable time-based failure.
- Difficulty timing and the client countdown still work when rewards are graded by mistakes.

### 21.5 Loot Settlement

- `source_rolls = 1` matches normal vanilla behavior.
- `source_rolls = 3` generates only two additional source-table rolls.
- `source_luck_bonus` affects only additional source rolls; base loot keeps its original probabilities.
- Fixed random probability entries without `quality` weighting are unaffected by `source_luck_bonus`.
- `bonus_rolls` generates the requested number of reward-table rolls.
- Different rolls use different deterministic seeds.
- Duplicate success packets distribute rewards only once.
- Full containers do not cause rewards to overwrite existing items.
- Manual locks do not duplicate existing items.
- Double chests do not distribute once per half.
- A Lootr player cannot claim the same reward repeatedly.
- Startup and gameplay work without Lootr installed.

### 21.6 Migration and Reloading

- Schema 1 locks can be upgraded and opened.
- `/reload` changes reward rules for newly generated locks.
- `/reload` does not change saved reward snapshots on existing schema 2 locks.
- Existing locks retain saved reward rules after a reward data pack is removed.
- If a saved reward-table ID becomes invalid, safely skip that extra reward and complete the unlock.

## 22. Acceptance Criteria

The completed implementation must satisfy all of the following:

- The three mistake-based minigames choose rewards using server-validated mistakes.
- Pipe locks choose rewards using server time.
- Data packs can define reward tiers separately from failure thresholds.
- `failure_at = -1` has stable semantics and does not disable other session validation.
- `source_rolls` can generate multiple complete source-table rolls.
- `bonus_rolls` can generate multiple rolls of a separate reward table.
- Failure grants no rewards, and success never grants duplicates.
- Closing the GUI, disconnecting, and reopening cannot refresh performance metrics.
- Double chests settle rewards once.
- Vanilla and Lootr container behavior is defined and verified.
- Old locks and data packs migrate safely.
- Invalid data packs do not crash the server or accidentally increase rewards.

## 23. Outside the Initial Scope

- A KubeJS API.
- Client-determined rewards.
- Directly editing or rewriting other mods' loot-table JSON files.
- Using GUI frame rate to calculate pipe time.
- Using rotation count as the default pipe reward metric.
- Duplicating existing container items as rewards.
- Unlimited `source_rolls` or `bonus_rolls`.
- Reward affixes that automatically unlock containers or skip minigames.
